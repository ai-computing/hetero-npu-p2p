# 길이별 배치 구성·조기 응답 시험 (2026-10-15~16 UTC)

## 확인된 개선

같은 KONI 이종 PD 하드웨어와 HTTP 측정 경계에서, 혼합 길이32요청의 처리량 중앙값이 **65.84 → 74.76 tok/s (+13.55%)**로 증가했다. B4 전체 슬롯 연산 중 유효 출력 생성 비율은 **64.52% → 81.08%**로 높아졌다. 이 비율은 배치 낭비를 나타내는 지표이며 MFU나 하드웨어 활용률이 아니다.

| 방식 | 처리량 중앙값 tok/s | 3회 범위 | 출력32 응답시간 중앙값 | 출력128 응답시간 중앙값 |
|---|---:|---:|---:|---:|
| FIFO, 배치 전체 완료 후 응답 |65.84|64.80–66.02|19.71초|27.37초|
| FIFO, 요청 완료 즉시 응답 |65.22|65.06–69.44|12.96초|27.28초|
| 길이별 배치, 요청 완료 즉시 응답 |74.76|74.42–80.86|15.00초|22.13초|

조기 응답만으로도 짧은 요청의 지연이 줄었다. 길이별 배치는 총 처리량과 출력64/96/128의 중앙 지연을 개선했지만, 출력32의 중앙 지연은 조기 응답만 적용한 경우보다 길었다. 처리량과 짧은 요청 우선 응답 사이에 선택이 필요하며 모든 지연 지표가 동시에 최적화된 것은 아니다.

추가 단회 점검에서 고정 출력128·16요청은 **100.89 → 100.83 tok/s**, 부분 배치3요청·출력32는 **36.34 → 37.23 tok/s**였다. 이 결과는 회귀 점검이며 단회 수치를 통계적 우위로 해석하지 않는다.

## 조건과 검증

- RNGD1 prefill, ATOM2/3 decode, 각 ATOM B4, context512, 동일 모델/컴파일 artifact.
- 입력140/167/227/271토큰. 혼합 출력32/64/96/128토큰을 각각8개씩 포함하는32요청 burst.
- 세 방식 모두 source staging, lookahead8, collection20ms, 동일 llm-d sidecar 사용. 반복마다 실행 순서를 회전시켰다.
- 전체334요청: 워밍업8, 혼합 비교288, 추가 점검38. 모든 요청에서 같은 B4 host-admission 기준 **전체 logits 정확히 일치**.
- DMA CQE 완료, 배치 실행 중 KV 덮어쓰기 없음, 오래된 완료 없음 확인. producer와 양쪽 worker 정상 종료. 단위시험35개 통과.
- 이번 시험에서는 전력을 측정하지 않았다. SLO 달성률, MFU 목표 달성, 단독 NPU 대비 새로운 우위 배율을 주장하지 않는다.

## 구현

llm-d는 prefill 요청의 출력 길이를1로 바꾼다. 따라서 RNGD에서 실제 prefill과 전송용 source 생성을 먼저 수행하되 ATOM 슬롯은 decode 요청의 출력 길이를 확인한 뒤 배정하도록 변경했다. 최대8개 대기 요청 안에서 가장 오래 기다린 요청을 포함해 출력 길이가 가까운4개를 선택한다.

완료된 요청에는 즉시 응답할 수 있지만 KV 버퍼·슬롯은 해당 B4 전체가 종료될 때까지 유지한다. 동작 중인 batch에 새 요청을 삽입하는 continuous batching은 구현하지 않았다. source를 대기열에 보관하므로 기존 즉시 admission보다 메모리를 더 유지한다. 이 경로는 별도 실험용 서버로 제공하며 기존 검증 서버의 기본 동작은 유지한다.

EOS 종료를 끄고 지정된 길이까지 생성한 시험이다. 실제 서비스의 `max_tokens`는 실제 생성 길이와 다를 수 있으므로 이득이 동일하다고 보장하지 않는다. 요청 취소·TTL 자동 정리는 여전히 실험 서버의 제한 사항이다.

## B8 가능성 점검: 별도의 decode 전용 시험

같은 ATOM2에서 host로 KV를 넣고128 decode step을 실행했다. B4는4개 prompt, B8은 같은 prompt4개를 두 번 넣었다. 각1회 워밍업+3회 측정이며 prefill·host KV 복사·P2P·HTTP 시간은 제외한다.

| 배치 | decode 처리량 중앙값 | step 시간 중앙값 |
|---|---:|---:|
| B4 |56.42 tok/s|70.54ms|
| B8 |103.54 tok/s|77.04ms|

B8의 decode 처리량은 B4 대비 **1.84배**였다. 모든 반복에서 전체 logits가 B4 기준과 정확히 일치했고, 실행 중 rbln-smi 관찰값은14.7/15.7GiB였다. 두 배의 배치 크기로 단일 요청 step 지연은 증가한다. 이는 동일 배치 비교가 아니라 배치 크기 변경에 따른 처리량/지연 절충 시험이다.

빌드 스크립트는 파일 저장 후 의도적으로 던진 중단 예외가 SDK CPU fallback에 잡혀 실패로 종료됐다. 이 실패 결과를 보존했다. 생성된 artifact를 새 프로세스에서 실제 적재·실행하여 별도로 유효성을 확인했다. B8 P2P export/import와 llm-d 통합은 이번 검증에 포함하지 않았고, 기존 B4 서버를 B8로 바꾸지 않았다. 다음 후보는 이 B8 artifact를 기존 완료 확인·버퍼 소유권 규칙을 유지하면서 PD 경로에 연결하는 것이다.
